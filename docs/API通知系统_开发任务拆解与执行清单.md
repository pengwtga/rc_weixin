## 0. 技术选型与前置约定

| 项 | 选择 | 理由 |
|---|---|---|
| 语言/框架 | Java 17 + Spring Boot 3.x | 团队主流栈；`HttpClient` 原生、事务与连接池生态成熟 |
| 存储 | MySQL 8.0（InnoDB） | 需要 `FOR UPDATE SKIP LOCKED`（8.0+ 才有） |
| 迁移 | Flyway | DDL 可版本化，评审时能直接看 schema 变更 |
| HTTP 客户端 | JDK `java.net.http.HttpClient` | 无需额外依赖；超时控制精细（connect/read/total） |
| 测试 | JUnit 5 + Testcontainers + WireMock | Testcontainers 保证 `SKIP LOCKED` 在真 MySQL 上被验证；WireMock 模拟 429/5xx/超时 |
| 部署 | Docker Compose（app + mysql） | 评审者 `docker compose up` 即可跑通，降低验证门槛 |
| 可观测 | Micrometer + Prometheus 端点 | 指标定义本身就是设计说明的一部分 |

> 换 Go/Python 时：**模块划分与任务依赖不变**，只需替换"框架/容器/客户端"三行的具体实现项。

**全局约定**
- 单体 + 分模块（`ingest` / `store` / `dispatch` / `policy` / `admin` / `common`），模块间只通过接口调用，不共享可变状态（为将来拆分留缝，但现在不拆）。
- 所有对外接口版本前缀 `/v1`。
- 时间统一 UTC 存储、`DATETIME(3)` 毫秒精度。

## 1. 拆解原则（为什么这么切）

1. **纵向切片优先**：先打通"提交 → 落库 → 投递 → 成功"这一条最窄的端到端链路（M1），再回头补重试、熔断、死信。目的是**尽早拿到可运行的东西**，避免"六个模块都写了一半但跑不起来"。
2. **正确性先于功能**：租约与崩溃恢复（T4.3）排在熔断、优先级之前。因为它们一旦错了，后面所有测试结论都不可信。
3. **可验证性驱动**：每个任务都写清 DoD，且 DoD 尽量是"能用命令/测试证明"的，不是"已实现"。
4. **文档即交付**：AI 会话记录、README、设计文档不是收尾工作，是作业的核心评分项，必须排进计划（T9.x），不能"最后有空再写"。

> **Flyway 是干什么的（与"换消息组件"无关）**：数据库 schema 的版本管理——每次改表 = 新增一个 `Vn__xxx.sql`，应用启动时按序执行未应用的迁移。三个收益：① schema 变更进 code review，谁在何时改了什么有历史可查；② 新环境（评审现场、同事本机）一条命令把库建到最新，不需要手工执行 SQL；③ 评审者直接看到 schema 演进过程——这本身就是"真实工程经验"的证据。**它不服务换 MQ**：换消息组件是应用层改动（到期扫描换成消费者，见设计文档 §7 V2），notification 表从"队列"退回"状态存储"，schema 基本不动。Flyway 的成本是一次接入半天 + 之后每改一次表加一个文件，唯一纪律是已提交的迁移文件不可再改（checksum 校验）。
| T1.5 | 统一错误响应与全局异常处理 | `ApiError` | 所有 4xx 返回结构化错误码，便于调用方判断 | T1.1 | S |

> **归档任务在解决两个问题（都不是"顺手清理"）**：① **合规**——注册/付款事件的 body 含手机号、邮箱、金额，"PII 最小留存"是 D10 的硬要求，保留期一到必须清明文（`body_sha256` 保留供排查）；② **扫描效率**——到期扫描走 `(status, next_attempt_at)` 索引，已完结行留在热索引里会拉深 B+ 树、降低 buffer pool 命中率，且 MEDIUMBLOB 溢出页占空间。首版只清 body（UPDATE 置空）；到 V1（日 > 300 万）再把已完结行整体搬到归档表。之所以不用分区表，见下一条坑。

> **踩过的坑（写进 README 的"决策记录"）**：MySQL 分区表要求唯一键包含分区列，而 `uk_idem` 与"按 `created_at` 分区"冲突。所以首版**不分区**，改用归档任务控制表大小。这个约束不实际试一次不会发现。

## 5. 风险与预案

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| `SKIP LOCKED` 行为与预期不符（版本/隔离级别） | 中 | 高（重复投递） | 先写一个最小复现用例（T8.4），确认后再写业务逻辑；MySQL 需 8.0+ 且用 `READ COMMITTED` 或默认 RR 均可，但必须实测 |
| 租约 < HTTP 超时导致双投 | 中 | 高 | T4.3 启动自检直接拦住，不允许配置出这种组合 |
| 熔断跳过把 `attempt_count` 烧光 | **高** | 高 | 单独写测（T5.7）盯这一条，这是最常见的实现错误 |
| 时间不够，功能做不完 | 高 | 中 | 按 §6 顺序裁剪，**优先保正确性与文档，砍功能** |
| AI 生成的代码"看起来对"但语义错（尤其重试/租约） | 高 | 高 | 所有涉及"计数、时间、锁"的代码必须自己逐行读一遍并补测试；不接受"测试通过即正确" |
| 评审者环境跑不起来 | 中 | 高 | Docker Compose 一把起；README 在干净容器里验证过 |
| AI 会话记录与设计文档对不上 | 中 | 高 | T9.3 以真实导出为准，反向校准设计文档 §6，不编造 |

## 9. AI 协作方式（记录怎么攒，别事后补）

作业明确要"AI 会话记录"，**事后凭记忆补写一定失真**。执行时按这三条攒：

1. **按阶段切会话**：需求分析、方案设计、编码排错各开一段，导出为独立 md，标题写清"这一轮我要解决什么"。
2. **每个被否决的 AI 建议，当场记三行**：
   ```
   AI 建议：第一版用 Kafka 做投递队列
   我的判断：不采纳 —— 100 QPS 下 Kafka 是负资产；重试要自造延迟 topic，复杂度搬家
   依据/验证：容量估算见设计文档 §8；写 POC 对比过部署成本
   ```
   这三行是设计文档 §6 的原料，也是评委会重点看的东西。
3. **保留 AI 的错误输出，不要美化**：把"AI 给的错误代码 + 我怎么发现 + 怎么修正"原样留下。**这比展示一堆正确代码更有说服力**，因为它证明你在审查而不是复制。

> 提醒：本次对话本身也应计入记录（属"需求分析 + 方案设计"阶段）。导出时把两份文档的产出过程一并带上。
