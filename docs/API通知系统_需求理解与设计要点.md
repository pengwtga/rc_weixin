# API 通知系统 —— 需求理解与设计要点

> 本文对应作业要求中的「README 或设计文档」部分。  
> 目标不是证明方案功能齐全，而是把**判断依据**摊开来：为什么这样切边界、为什么这样选语义、为什么不采纳某些看起来更"专业"的方案。

---

## 0. 一句话结论

这是一个**可靠出站 HTTP 投递**问题，不是消息总线问题。  
所以核心只有三件事：**请求先落盘（不丢）、投递有租约（不重复卡死）、失败有分级（不白重试）**；  
其余一切（模板渲染、业务编排、多租户、可视化后台）都在边界之外。

---

## 0.5 我如何读这份需求

先说读法：拿到一份一页纸的需求，我分两步——

1. **找出句子背后不可变的事实**（丢一条的代价、调用方是否关心返回值、外部 API 是否同构）—— 这些决定设计走向，见 §1；
2. **找出文档没说、但决策又绕不开的信息** —— 这些不能猜，必须显式处理。

第二步是本节的重点。这份需求里有三处信息空白，我的处理方式各不相同，但原则一致：

| 空白                            | 我没有做的事                 | 我做的事                                                                  | 落点        |
| ----------------------------- | ---------------------- | --------------------------------------------------------------------- | --------- |
| **企业内到底几个业务系统？与外部供应商是否一一对应？** | 猜"三个系统对三个系统"然后按 1:1 设计 | 声明未知；把 `caller_id` 定义为"提交身份"而非"部署单元"，使 1 个或 3 个都不改结构；列出需向业务方确认的 2 个问题 | §2.4、§9.3 |
| **投递量级是多少？**                  | 拍一个数字直接选型              | 给出假设与推导过程；做敏感性分析，证明结论对 3 倍误差鲁棒、只在 10 倍时翻转                             | §8        |
| **调用方有没有顺序诉求？**               | 默认"大概需要"而设计一个排序机制      | 默认**没有**（三个场景均未提及）；把"何时需要加回来"写成可验证的触发条件                               | §3.5、§9.4 |

一句话总结这个原则：

> **缺信息时，正确的动作不是猜一个前提往下推，而是：声明未知 → 证明设计不依赖它 → 写明向谁确认什么。**

这条原则还决定了两处取舍的方向：`caller_id` 的语义设计（§2.4）和 `ordering_key` 的删除（§3.5）——前者是"不依赖未知"的正面例子，后者是"不为想象的需求付复杂度"的例子。如果评审者对这两处有不同判断，§3.5 和 §9 里都留了可反驳的依据，欢迎推翻。

## 1. 我对需求的重新表述

### 1.1 问题的本质

原始描述是三句业务场景（广告归因、CRM 状态同步、库存扣减），但它们指向同一个技术抽象：

```
业务系统 --(已渲染好的 HTTP 请求)--> [本系统] --(尽可能可靠地)--> 外部供应商 API
```

三个关键事实决定了设计走向：

| 事实                             | 设计含义                                       |
| ------------------------------ | ------------------------------------------ |
| 业务系统**不关心返回值**                 | 无需同步等待结果 → 接入侧只需"已接收"确认，投递异步化              |
| 但业务系统**关心"有没有送达"**             | 不能 fire-and-forget 返回 200，必须有可查询的投递状态与唯一单号 |
| 外部 API **地址/Header/Body 各不相同** | 本系统不做格式转换，只做**透传**；格式化责任在业务侧               |

第三条是最容易被做歪的地方。一旦本系统开始管"模板渲染"，就变成了半个业务中台：要管变量定义、版本、预览、回滚，而收益只是替业务系统省一次 `objectMapper.writeValueAsString()`。**不做。**

### 1.2 由场景反推出的硬约束

1. **不能丢**：付款成功通知 CRM 失败，等于用户付了钱但状态没同步。丢一条的成本远高于多投一条。
2. **不能卡死**：某个供应商 API 挂了 3 小时，不能拖垮其他供应商的投递，也不能拖垮接入侧。
3. **不能重复放大**：外部系统大多**不是**幂等的。我们不能"为了可靠"无限重试把一个 400 错误打成雪崩。
4. **必须可追责**：出问题时要能回答"这条到底投了几次、每次返回什么、为什么还在重试"。
5. **对调用方友好**：业务系统可能超时重试提交，同一事件不能变成两条通知。

### 1.3 我明确读出来的非目标

- 不是业务事件总线（不订阅、不分发、不做事件驱动架构的枢纽）
- 不是 ETL / 数据同步工具（不比对、不补偿业务数据差异）
- 不是 API 网关（不做协议转换、不做聚合）

## 2. 系统边界

### 2.1 本系统解决的问题

| # | 问题      | 解决到什么程度                       |
| - | ------- | ----------------------------- |
| 1 | 请求持久化   | 接入即落库，返回后进程崩溃也不丢              |
| 2 | 异步投递    | 独立投递引擎，与接入侧解耦                 |
| 3 | 失败重试    | 按错误类型分级 + 指数退避 + 重试预算         |
| 4 | 崩溃恢复    | 租约（lease）机制，worker 挂掉后任务被重新认领 |
| 5 | 端点隔离    | 单供应商故障不影响其他供应商（并发隔离 + 熔断）     |
| 6 | 重复提交防护  | 调用方幂等键去重                      |
| 7 | 最终失败兜底  | 死信 + 告警 + 人工重放                |
| 8 | 可观测与可追责 | 状态查询、逐次投递记录、指标                |
| 9 | 出站安全    | SSRF 防护、凭证加密、PII 最小留存         |

### 2.2 我明确不解决的问题（以及为什么）

| 不解决                     | 理由                                                                                                                                    |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **端到端「恰好一次」**           | 物理上不可能。下游处理成功但响应超时，我们只能重试；要消除重复必须下游配合幂等。**投入极大、收益为零**，改为契约化：我们保证至少一次 + 携带幂等标识，下游保证幂等。                                                 |
| **下游业务是否真的生效**          | 我们只能观测 HTTP 层。CRM 返回 200 但内部写库失败，是 CRM 的问题。做"业务对账"就是越界。                                                                               |
| **消息顺序保证**              | **一条都不做** —— 既不做全局有序，也不做"同实体不并发"的弱有序（v1 中已删除 `ordering_key` 字段）。异步重试本身就会乱序，任何传输层保证都不足以让下游免于版本判断。顺序交下游按版本号/时间戳应用，我方只保证"至少一次"（推导见 §3.5） |
| **请求内容转换 / 模板渲染**       | 见 1.1。业务系统已经知道供应商格式，多一层转换就多一处需要同步维护的契约。                                                                                               |
| **供应商 API 的探活与 SLA 管理** | 我们不是监控系统。只做被动的失败率统计，不做主动探测与供应商评级。                                                                                                     |
| **重试策略的可视化编排**          | 首版用配置 + 少量预设档位（标准 / 长尾 / 快速失败）。做一个规则引擎是典型过度设计。                                                                                        |
| **按业务优先级排队 / 加权公平调度**   | 首版先到先投。等真的出现"营销通知挤占付款通知"再引入优先级队列，那时才有数据支撑分级标准。                                                                                        |
| **多租户计费、配额结算**          | 内部系统，只做限流保护自身，不做计量收费。                                                                                                                 |

### 2.3 一条必须讲清楚的边界线

> **可靠性止于「送达」，一致性由下游负责。**

我可以保证：只要供应商返回 2xx，我就标记成功；只要没拿到 2xx，我就按策略继续尝试。  
我**不能**保证：供应商收到两次时只处理一次。

所以接入协议里强制带上 `X-Notification-Id`（我方唯一单号）与 `X-Idempotency-Key`（调用方业务幂等键），并要求供应商侧（或对接方）以此去重。这条写进文档而不是假装不存在——**这才是"可靠"的真实含义**。

### 2.4 调用方建模：内部系统与外部系统不是一一对应

这一节回答一个**需求文档里没有答案、但直接决定接入设计**的问题：企业内部到底有几个业务系统？

**结论：文档给不出答案，而且这个答案不影响核心设计。** 我把它列为待确认假设（§9），并把设计做成对两种答案都成立。

#### 为什么推不出来

- 「企业内部多个业务系统」是**问题陈述**，不是系统清单。它只声明一件事：**调用方不止一个**。
- 三个例子是**事件清单**（注册 / 付款 / 购买），不是系统清单。同一个事件由哪个系统发出，取决于**团队怎么划分**，不取决于事件本身。

同一份文档至少能容纳三种映射，都说得通：

| 形态    | 内部                                                   | 外部 | 是否符合文档 |
| ----- | ---------------------------------------------------- | -- | ------ |
| A｜1:1 | 用户系统 → 广告；订阅系统 → CRM；订单系统 → 库存                       | 3  | 符合     |
| B｜多对多 | 用户中心 / 交易中心 / 商品中心 —— "付款"由交易发出，"Contact 状态"由客户主数据发出 | 3  | 符合     |
| C｜单体  | 一个 monolith 承载三个事件                                   | 3  | 符合     |

**我倾向 B，而不是 A。** 理由：外部系统的边界是**供应商的产品边界**，内部系统的边界是**团队组织边界**。两者按完全不同的原则划分，没有理由对齐。具体到三个场景：

- **广告转化回传**：转化数据在交易侧，内部对应方很可能是增长/营销或交易，不一定是"用户系统"；
- **CRM Contact 状态**：付款事件来自计费，Contact 主数据却归属客户中心 —— 往往分属两个团队；
- **库存变更**：订单调库存大概率是**同步内部 RPC**，只有"跨公司通知库存供应商"这一跳才需要可靠性保障。

所以"内部 3 个 ↔ 外部 3 个"是巧合，不是结构。

#### 这个不确定性为什么不影响设计

`caller_id` 就是为这件事存在的。它的语义是**提交身份**（一个 credential + 一个限流桶 + 一个归因标签），**不是部署单元**：

- 一个部署单元可以持有多个 `caller_id`（单体里营销和财务各申请一个 Key）；
- 多个部署单元可以共用一个 `caller_id`（同一团队的两个服务）；
- 因此"1 个还是 3 个"是**接入时注册几个 Key**，不是架构决策。

真正受影响的只有三个参数级的地方，都不改结构：

| 影响点  | 1 个系统                   | 3 个系统                       |
| ---- | ----------------------- | --------------------------- |
| 容量估算 | 事件总量不变                  | 事件总量不变                      |
| 隔离粒度 | 按 `target_url` 做并发隔离与熔断 | 额外可按 `caller_id` 限流，故障不互相拖累 |
| 故障归因 | 只能定位到"系统"               | 能定位到具体调用方，失败清单可按 caller 分发  |

#### 你的推论里有一处要修正

你说："每个系统发生的每个事件天然带有唯一状态，所以不存在分组问题。"

这句话拆成两半，一半对，一半不成立：

| 推论                  | 判断                                                                  |
| ------------------- | ------------------------------------------------------------------- |
| 事件唯一标识 → 不会**重复**投递 | ✅ 成立，这就是 `idempotency_key` 的作用                                      |
| 事件唯一标识 → 不会**乱序**到达 | ❌ 不成立。唯一性是"两个东西是不是同一个"（相等判断）；有序需要的是**同一实体的单调版本序列**（全序）。有 ID 不等于可比先后 |

更要紧的是：**乱序是我这一层制造的，不是业务层制造的。**

```
业务侧：t=0 发「注册」，t=1 发「付款」        —— 发送顺序完全正确
我方：  「注册」失败 → 退避 10 分钟后再试
        「付款」首次成功
到达顺序：「付款」先、「注册」后              —— 顺序被异步重试破坏
```

**引入异步 + 重试的那一刻，到达顺序就不再由发送端决定**，跟内部是单体还是微服务无关。你说的"微服务天然有序"只在**同步调用链**里成立；一旦经过我这个异步缓冲，这个性质就丢失了。

#### 但"内部 3 个系统"恰好让跨系统排序变得不可实现

如果真是 A 形态（1:1）：同一订单的两条通知分别由**订单系统**和**订阅系统**发出，两者互不知情。想在业务侧串行提交，就得让订单系统等订阅系统投递成功 —— 这是跨团队协调，比在通知系统里加一列难得多。

反过来，如果三个事件由**同一个系统**在同一事务后发出，业务侧串行提交才是可操作的。

**所以"内部到底 1 个还是 3 个"正好决定了"顺序能不能在业务侧解决"。而两种答案都不支持我在传输层做弱有序** —— 见 §3.5 的结论。

## 3. 整体架构

### 3.1 组件视图

```
                    ┌──────────────────────────────────────────────┐
 业务系统 A ─┐      │  接入层 Ingest API                            │
 业务系统 B ─┼─────▶│  · 鉴权(API Key) · 校验 · 幂等去重 · 限流      │
 业务系统 C ─┘      │  · 落库 → 202 Accepted + notification_no     │
                    └───────────────────┬──────────────────────────┘
                                        │ 写
                    ┌───────────────────▼──────────────────────────┐
                    │  MySQL（唯一事实来源）                         │
                    │  notification / delivery_attempt              │
                    └───────────────────┬──────────────────────────┘
                                        │ 认领（SKIP LOCKED + 租约）
                    ┌───────────────────▼──────────────────────────┐
                    │  投递引擎 Dispatcher（可多实例水平扩展）        │
                    │  ┌────────────┐  ┌───────────────────────┐   │
                    │  │ 到期任务扫描 │→│ Worker Pool            │   │
                    │  │ (poll 500ms)│  │ · 按 host 并发隔离      │   │
                    │  └────────────┘  │ · 超时预算 15s         │   │
                    │                   │ · 熔断器 per host      │   │
                    │                   └───────────┬───────────┘   │
                    │  失败分类 → 退避 → 重排 / 死信                 │
                    └───────────────────┬──────────────────────────┘
                                        │ HTTPS
                              ┌─────────▼──────────┐
                              │ 外部供应商 API      │
                              └────────────────────┘

 旁路：查询/重放 API · 指标(Prometheus) · 死信告警 · 归档任务
```

**关键点：**&#x63A5;入层与投递引擎之间**没有中间件**，靠数据库表衔接。这不是偷懒，见 4.3。

### 3.2 一次投递的完整生命周期

```
1. 业务系统 POST /v1/notifications
   Header: X-Api-Key, Idempotency-Key=order_paid:20261028:8837
   Body:   { target_url, method, headers, body }

2. 接入层：鉴权 → 校验 URL(SSRF) → 幂等检查
   ├─ 已存在 (caller_id, idempotency_key) → 返回 202 + 原 notification_no（不新建）
   └─ 不存在 → INSERT status=PENDING, next_attempt_at=now
   → 202 Accepted { notification_no, status: "PENDING" }

3. Dispatcher 轮询到期任务：
   UPDATE ... SET status=PROCESSING, lease_owner=?, lease_until=now+60s,
                  attempt_count=attempt_count+1
   WHERE id IN (SELECT id FROM notification
                WHERE (status IN ('PENDING','RETRY_WAIT') AND next_attempt_at<=now)
                   OR (status='PROCESSING' AND lease_until<now)   -- 崩溃回收
                ORDER BY next_attempt_at LIMIT 100 FOR UPDATE SKIP LOCKED)

4. Worker 执行 HTTP 调用（connect 3s / read 10s / total 15s 预算）
   · 记录 delivery_attempt（状态码、耗时、错误分类、响应片段 2KB）
   · 不跟随重定向（或最多 1 跳且重校验）

5. 结果分支：
   2xx                      → SUCCEEDED，lease 清除
   4xx(除 408/425/429)      → DEAD（永久失败，立即告警，不浪费重试预算）
   408/429/5xx/超时/连接错误 → RETRY_WAIT + next_attempt_at = now + backoff(n)
   attempt_count >= max     → DEAD（进死信）
   熔断中（host OPEN）        → next_attempt_at = now + 60s，**attempt_count 回退**（见 4.7）

6. 人工介入：GET 状态详情（含每轮 attempt）→ 体检端点 → replay（单条或按 caller+error_class 批量）
   → status 回 PENDING、replay_epoch+1、max_attempts 追加预算（详见 D8）
```

> 认领 SQL 的 `SKIP LOCKED` 与租约回收细节见 D4；重放的状态守卫与 `replay_epoch` 见 D8.4。

### 3.3 数据模型

```sql
CREATE TABLE notification (
  id               BIGINT UNSIGNED   NOT NULL AUTO_INCREMENT COMMENT '自增主键，仅内部使用；对外一律用 notification_no',
  notification_no  CHAR(26)          NOT NULL                COMMENT '对外唯一单号（ULID，26 字符）。日志、查询接口、注入下游的 X-Notification-Id 都用它',
  caller_id        VARCHAR(64)       NOT NULL                COMMENT '调用方（业务系统）标识，由 API Key 解析得到；用于鉴权、限流、幂等域与数据隔离',
  idempotency_key  VARCHAR(128)      NOT NULL                COMMENT '【事件级】幂等键：标识"这一次通知提交"，不是订单/用户的 ID。建议 <事件类型>:<事件唯一ID>，如 order_paid:pay_20261028_001。与 caller_id 组成唯一键，防同一事件被重复提交；同一订单的多条通知各用各的键（见 §3.6）',
  target_url       VARCHAR(2048)     NOT NULL                COMMENT '外部供应商 API 完整地址；落库前经 SSRF 校验（仅 HTTPS / 拒绝私网与回环 / 域名白名单）',
  http_method      VARCHAR(8)        NOT NULL DEFAULT 'POST' COMMENT 'HTTP 方法；白名单 POST/PUT/PATCH/DELETE/GET',
  headers_enc      MEDIUMBLOB        NULL                    COMMENT '请求头（JSON 的 UTF-8 字节）经 AES-256-GCM 密封：[1B版本][12B随机IV][密文+16B tag]，AAD=单号+字段名。含供应商凭证，查询接口脱敏返回，日志不打印（D10.2）',
  body_enc         MEDIUMBLOB        NULL                    COMMENT '请求体原始字节经 AES-256-GCM 密封（格式同 headers_enc，AAD=单号+"body"）。投递时解密还原；保留期由归档任务控制（成功 24h / 失败 7d 后置 NULL）',
  body_fingerprint CHAR(64)          NOT NULL                COMMENT '【密钥化指纹】body 明文的 HMAC-SHA256（十六进制，64 字符）。用途：归档清空 body 后仍可回答"当时发出的内容是否与某份候选一致"；相同明文必须得到相同指纹，因此不可加随机盐（D10.3）',
  status           VARCHAR(16)       NOT NULL DEFAULT 'PENDING' COMMENT '状态机：PENDING/RETRY_WAIT/PROCESSING/SUCCEEDED/DEAD/CANCELED；仅 DEAD 可由 replay 回到 PENDING',
  attempt_count    SMALLINT UNSIGNED NOT NULL DEFAULT 0      COMMENT '累计已消耗的尝试次数，在【认领时】自增（非完成后）；熔断跳过需回退；达到 max_attempts 转 DEAD',
  max_attempts     TINYINT UNSIGNED  NOT NULL DEFAULT 10     COMMENT '重试预算上限，由 RetryPolicy 档位（STANDARD/LONG_TAIL/FAST_FAIL）决定；replay 时按档位追加',
  replay_epoch     SMALLINT UNSIGNED NOT NULL DEFAULT 0      COMMENT '重放轮次。0=首轮，每次 replay +1；用于区分 attempt 的归属，避免唯一键冲突（见 D8.4）',
  next_attempt_at  DATETIME(3)       NOT NULL                COMMENT '下次可投递时刻（UTC）。到期扫描的唯一排序键；退避、熔断跳过、摊平重放都改这个字段',
  lease_owner      VARCHAR(64)       NULL                    COMMENT '当前持有租约的实例 ID；NULL 表示未被占用。仅用于排查，不参与认领的 CAS 判断',
  lease_until      DATETIME(3)       NULL                    COMMENT '租约到期时刻（UTC，= 认领时刻 + 60s）。过期即视为持有者已崩溃，可被其他实例重新认领（见 D4）',
  last_error_class VARCHAR(32)       NULL                    COMMENT '最近一次失败的归一化分类：TIMEOUT/DNS/TLS/CONN_REFUSED/REDIRECT_REFUSED/HTTP_4XX/HTTP_5XX；也是失败通知的路由依据',
  last_status_code SMALLINT          NULL                    COMMENT '最近一次收到的 HTTP 状态码；网络层失败时为 NULL，与 last_error_class 配合排查',
  created_at       DATETIME(3)       NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时刻（UTC），接入层落库时间',
  updated_at       DATETIME(3)       NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '最后更新时刻（UTC），状态或租约变更时自动刷新',
  PRIMARY KEY (id),
  UNIQUE KEY uk_idem        (caller_id, idempotency_key) COMMENT '接入侧幂等：同调用方 + 同业务键只允许一条，冲突时查回原单号',
  KEY idx_due               (status, next_attempt_at)    COMMENT '到期任务扫描（覆盖 PENDING / RETRY_WAIT）',
  KEY idx_lease             (status, lease_until)        COMMENT '租约过期回收扫描（PROCESSING 且 lease_until < now）',
  KEY idx_caller_status_ct  (caller_id, status, created_at) COMMENT '业务方按游标拉取失败清单（status=DEAD + created_at > cursor）'
) ENGINE=InnoDB COMMENT='通知投递任务表 —— 本身即队列：SKIP LOCKED 认领 + 租约实现可见性超时';

CREATE TABLE delivery_attempt (
  id               BIGINT UNSIGNED   NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  notification_id  BIGINT UNSIGNED   NOT NULL                COMMENT '所属通知，关联 notification.id（用整数关联而非 notification_no，避免字符串索引与关联代价）',
  replay_epoch     SMALLINT UNSIGNED NOT NULL DEFAULT 0      COMMENT '所属重放轮次，与 notification.replay_epoch 对应；同通知不同轮次的 attempt_no 允许重复',
  attempt_no       SMALLINT UNSIGNED NOT NULL                COMMENT '本轮内第几次尝试，从 1 开始；跨轮次由 replay_epoch 区分（累计次数见 notification.attempt_count）',
  started_at       DATETIME(3)       NOT NULL                COMMENT '本次尝试开始时刻（UTC）',
  duration_ms      INT               NULL                    COMMENT '本次尝试耗时（毫秒），含 DNS/TLS/连接/传输；超时场景记为超时上限',
  status_code      SMALLINT          NULL                    COMMENT 'HTTP 响应状态码；网络层失败（超时/DNS/TLS/连接拒绝）时为 NULL',
  error_class      VARCHAR(32)       NULL                    COMMENT '失败归一化分类，成功为 NULL：TIMEOUT/DNS/TLS/CONN_REFUSED/REDIRECT_REFUSED/HTTP_4XX/HTTP_5XX',
  response_snippet VARCHAR(2048)     NULL                    COMMENT '响应体前 2KB（截断存储），用于查看供应商真实返回；不含我方请求中的凭证',
  PRIMARY KEY (id),
  UNIQUE KEY uk_n_epoch_attempt (notification_id, replay_epoch, attempt_no) COMMENT '同通知同轮同序号只允许一条，防止重复登记',
  KEY idx_n (notification_id) COMMENT '按通知查全部投递记录（状态详情接口一次查全）'
) ENGINE=InnoDB COMMENT='逐次投递明细 —— 只追加不更新，用于追责、排查与 SLA 统计';
```


**几个字段的取值来自设计约束，不是随手定的**：

| 字段                                    | 约束来源                                                   |
| ------------------------------------- | ------------------------------------------------------ |
| `lease_until`（60s）                    | 必须 > HTTP 总超时（15s）+ 余量，否则双投率暴涨；启动时断言（D4.5 / T4.3）      |
| `attempt_count` 认领时自增                 | 崩溃时无人执行"完成后自增"，否则毒消息无限循环（D4.5）                         |
| `next_attempt_at` 用 UTC `DATETIME(3)` | 毫秒精度支撑秒级退避；统一 UTC 避免时区与夏令时歧义                           |
| `replay_epoch` 进唯一键                   | 不加则重放时 `(notification_id, attempt_no)` 撞键，重放直接失败（D8.4） |
| `idx_caller_status_ct`                | 支撑 T5.8 失败清单的游标翻页；只靠 `idx_due` 会让该查询走全表                |

> **上表是 V4 迁移后的最终形态**。`body_sha256 → body_fingerprint` 的改名与 `headers_enc` 由 `TEXT` 改 `MEDIUMBLOB` 由 `V4__encrypt_payloads.sql` 完成——已提交的 V2 不改写，演进只能追加迁移（Flyway 的纪律，也是评审能看到的 schema 变更历史）。

> **实测记录（MySQL 8.0.46）**：以上 DDL 与 D4 的认领 SQL 已在真实实例上跑通，两处只有跑了才知道的细节——  
> ① `status` 必须给 `DEFAULT 'PENDING'`，否则任何 INSERT 都要显式带状态，容易漏；  
> ② D4 的 `LIMIT :batchSize` 是 **JDBC 绑定参数**，MySQL 不允许 `LIMIT` 使用用户变量（`LIMIT @n` 直接语法错误）。  
> 实测结果：第一轮认领 `attempt_count=1 / lease_owner=worker-1`；把 `lease_until` 改到过去后，第二轮由 `worker-2` 接管且 `attempt_count=2` —— 崩溃回收链路的行为与 D4 描述一致。

### 3.4 状态机

```
        ┌──────────┐  claim   ┌────────────┐  2xx   ┌───────────┐
   ────▶│ PENDING  │─────────▶│ PROCESSING │───────▶│ SUCCEEDED │
        └────┬─────┘          └─────┬──────┘        └───────────┘
             │                      │ 可重试失败
             │                      ▼
             │              ┌──────────────┐  退避到期 / 重新 claim
             │              │  RETRY_WAIT  │────────┐
             │              └──────┬───────┘        │
             │                     │ 超预算/永久失败 │
             │                     ▼                │
             │              ┌──────────────┐        │
             └─replay───────│     DEAD     │────────┘
                            └──────────────┘
   PROCESSING 且 lease_until < now → 被重新 claim（崩溃回收）
```

`SUCCEEDED` / `DEAD` 是终态，只能通过显式 replay 回到 `PENDING`。

### 3.5 为什么首版不做顺序保证（以及真要做的两条路）

（若还在区分"事件唯一 ID"和"顺序"，先看 §2.4 末尾那一段。）

#### 结论

**不提供任何顺序保证**：既不做全局有序，也不做"同一实体不并发"的弱有序。`ordering_key` 字段在 v1 中**删除**。

这是我整套设计里唯一一处"先加、后删"的决定。**过程比结论更值得记录**：一个字段先被设计出来、被写进 DDL、然后被自己的判据否掉——这比一开始就不写它更能说明判据是活的。

#### 理由一｜传输层的有序本来就不可靠

即使我把顺序做到极致，下面三种情况仍然乱序，且都不在投递链路的控制内：

1. **人工 replay 一条 `DEAD`**（D8）—— 重放必然晚于所有后续通知；
2. **同一实体的通知被投给不同 `target_url`**（下单给广告、付款给 CRM）—— 是两条完全无关的连接；
3. **多实例 + 连接池复用** —— 同一批任务由不同 worker 在不同时刻发出。

既然下游无论如何都必须能处理乱序（按业务版本号、`created_at`、或幂等键去重），那传输层的有序就是**冗余的**：它不能让下游省掉这段逻辑，只能让下游**以为**可以省掉。

#### 理由二｜弱有序是最糟的一档：降低撞车概率，但不建立正确性

"同 key 不并发"能减少乱序的**概率**，但一条重试就会打破它：

```
t=0   #1（order:8837）失败 → RETRY_WAIT，10 分钟后重试；不再处于 PROCESSING
t=0   #2（order:8837）立刻被认领
t=1   #2 投递成功
t=600 #1 重试成功
      → 实际到达顺序：#2 → #1，顺序已破
```

一个"看起来保证了顺序、实际只在多数情况下成立"的机制，比"明确不保证"更危险：**它会被依赖**。等业务方按"填了就保序"写代码，问题会以最难排查的形式出现——偶发、低频、无法复现。

#### 理由三｜成本不是零，只是被藏起来了

删掉它省下的不是一列，而是：

- 认领 SQL 上多一个 anti-join（**热路径**，每 500ms 跑一次）；
- 一个 `(ordering_key, status, next_attempt_at)` 索引；
- 一份"填了但不保序"的接入说明 —— 而这份说明本身就暴露了问题：**一个字段要靠长篇解释才懂，说明它没定清**（这正是 §3.6 的教训）。

#### 如果将来真需要，两条路（都不改现有结构）

| 方案         | 做法                                                                   | 代价                                          |
| ---------- | -------------------------------------------------------------------- | ------------------------------------------- |
| 认领 SQL 加条件 | "同 key 内不存在更早的未完成任务"才可认领                                             | anti-join 变重，需补索引                           |
| 独立槽位表      | `ordering_slot(ordering_key PK, notification_id, lease_until)`，认领前抢槽 | 多一张表，但可观测（能看到每组被谁占着），也便于把同 key 路由到固定 worker |

两者都是**加列 + 加索引**级别，无数据迁移。所以"先不做"不是把问题推后，是**留了一张很便宜的回头票**。

触发条件（写进 §9）：某个调用方明确提出"同一实体的两条通知必须按序到达"，**并能说清乱序的具体业务后果**。没有这个具体场景，就不做。

#### 那顺序应该在哪解决

| 层次         | 做法                           | 适用                                     |
| ---------- | ---------------------------- | -------------------------------------- |
| **下游（推荐）** | 下游按事件版本号/时间戳应用，乱序到达也能收敛到正确状态 | 绝大多数情况；而且反正必须做                         |
| 业务侧        | 前一条投递成功后再提交下一条（查状态接口确认）      | 事件由**同一系统**发出，能串行等待                    |
| 我这边        | 槽位表 / 队首可见                   | 仅当上面两条都不可行，且愿意承担 head-of-line blocking |

head-of-line blocking 的代价说清：队首那条一直失败，整组都被堵住，最长堵到重试预算耗尽（STANDARD 档约 3.5 小时）——**一个供应商的偶发故障，会让同一实体的后续所有通知一起延迟**。

### 3.6 幂等键的粒度（最容易写错的一处）

`idempotency_key` 看着像"业务主键"，实际是"**这一次通知提交**"的标识，比订单/用户低一层。混淆会导致**静默丢消息**。

> **一句话**：它认的是「**这一次通知**」，不是「这个订单」。

#### 订单 8837 在表里是三行，不是一行

以订单 8837 走完「下单 → 付款 → 发货」为例，业务系统会提交**三次**，表里落**三条记录**：

| notification_no（我方生成） | idempotency_key（对方填）             | 投递给谁            |
| --------------------- | -------------------------------- | --------------- |
| `01J8XA...A1`         | `order_created:evt_8837_created` | 广告系统（转化回传）      |
| `01J8XA...A2`         | `order_paid:pay_20261028_001`    | CRM（Contact 状态） |
| `01J8XA...A3`         | `order_shipped:shp_20261029_009` | 库存系统（库存变更）      |

三条的 `idempotency_key` **互不相同** → `uk_idem(caller_id, idempotency_key)` 不冲突，**三行都能插入**。

所以"一个订单只能创建一条通知"这个推论不成立 —— **唯一键限制的是"同一次事件被重复提交"，不是"同一订单的多条事件"**。

#### 它防什么 / 不防什么

|          | `idempotency_key`                                         |
| -------- | --------------------------------------------------------- |
| 粒度       | **一次通知提交**（事件级）                                           |
| 谁生成      | 调用方（必须由业务事件的天然 ID 构成）                                     |
| 防什么      | 业务系统**超时重试 / 消息重复消费**导致同一条通知提交两次                          |
| **不防什么** | ① 同一订单的不同事件 —— 那些**应该**各建一条；② 乱序 —— 那是另一个问题，且已明确不解决（§3.5） |
| 唯一键      | `UNIQUE (caller_id, idempotency_key)`                     |
| 为 NULL   | 不允许（必填）                                                   |
| 缺失的后果    | 同一条通知投递多次（下游重复扣库存）                                        |

#### 幂等键怎么组成（这里写错会丢消息）

**规则：用它所指的那个事件的天然唯一 ID。**

| 业务事件   | ✅ 推荐写法                        | 依据                 |
| ------ | ----------------------------- | ------------------ |
| 付款成功   | `order_paid:pay_20261028_001` | 支付流水号天然唯一          |
| 注册成功   | `user_signup:uid_10231`       | 用户注册只发生一次          |
| 库存扣减   | `stock_out:so_20261028_0093`  | 出库单号唯一             |
| 订单状态变更 | `order_status:8837:v3`        | 状态版本号区分"同一状态的多次发生" |

**三个必须避免的反例**：

1. **拿订单号当幂等键** → `idempotency_key = "8837"`。  
   后果：这个订单的"下单""付款""发货"三条通知，后两条会被**判为重复直接丢弃**。这是最隐蔽的丢消息方式，因为接口返回 202，业务方以为成功了。  
   （你刚才的疑问正是这个反例 —— 说明这个坑很真实，值得写进文档。）
2. **用时间戳或随机数** → `idempotency_key = "8837_" + System.currentTimeMillis()`。  
   后果：每次重试都是新键，唯一键**完全失效**，等于没有幂等保护。
3. **用「订单号 + 当前状态」但状态会回退** → 退款后再次付款，状态又回到 `PAID`，第二次付款被判为重复 → 丢一条通知。  
   修正：加版本号或流水号，让"同一状态的多次发生"能区分开。

#### 责任划分

| 字段                      | 谁生成     | 理由                                       |
| ----------------------- | ------- | ---------------------------------------- |
| `notification_no`（ULID） | **我方**  | 我们的单号体系，用于日志、查询、注入下游 `X-Notification-Id` |
| `idempotency_key`       | **调用方** | 只有业务系统知道"这次事件唯一是什么"                      |
| `idempotency_key`       | **调用方** | 只有业务系统知道"这次事件唯一是什么"                      |

**我方无法替调用方生成幂等键** —— 一生成就退化成随机数，幂等保护失效。所以接入时必须校验：

- 非空、≤128 字符；
- **强制两段式 `<事件类型>:<事件唯一ID>`**（冒号分隔），事件类型必须在已注册枚举内。  
  这条格式校验能直接挡住反例 1（`order_id` 直接当键没有冒号，被拒）和反例 2（拼时间戳可通过，需在接入评审时人工确认）；
- 幂等键在**同一 `caller_id` 内**唯一即可，不同业务系统提交同一事件互不影响（`caller_id` 已参与唯一键）。

## 4. 核心设计要点

每一条都按 **做法 / 为什么 / 代价 / 没选的替代方案** 展开。

### D1｜同步接入 + 异步投递（202 Accepted）

**做法**：接入层只做"校验 + 落库"，成功返回 `202 Accepted` + `notification_no`；投递完全异步。

**为什么**：供应商 API 的可用性不可控（3s 超时很常见）。若接入侧同步等待，一个慢供应商就会把业务系统的线程池打满——这是把外部故障引入内部最典型的路径。

**为什么不是 200**：`202` 语义上准确表达"已接收、未完成"，且返回单号，让"不关心返回值"和"要能查状态"两个诉求同时成立。

**代价**：业务系统拿到的不是结果，需要（可选地）查状态；需要一份清晰的对外状态语义。

**没选**：异步回调/webhook 通知业务系统投递结果 —— 首版不做，因为业务系统明确说"不关心返回值"。等真有人需要，再加一层可选回调。

---

### D2｜投递语义：至少一次（at-least-once）+ 幂等键

**做法**：明确声明 at-least-once。绝不承诺 exactly-once。配套两件事：

1. 接入侧幂等（`caller_id + idempotency_key` 唯一索引）：业务系统重试提交不会产生第二条；
2. 投递侧幂等标识（`X-Notification-Id`）：下游可选去重。

**为什么**：exactly-once 需要跨进程的两阶段确认，且必须下游配合。我们能做到的极限是"下游 2xx 后不再重投"，而"下游已处理但响应丢了"这一窗口无法消除。

**代价**：下游必须容忍重复。这是**契约**，不是缺陷，必须写进接入文档，并在对接时确认。

**没选**：本地去重表 + 请求指纹比对来"假装 exactly-once" —— 只能防住自己的重复投递，防不住超时导致的重复，属于给假安全感。

---

### D3｜用「数据库即队列」，而不是第一版就上 MQ

**做法**：`notification` 表本身就是队列。调度靠 `SELECT ... FOR UPDATE SKIP LOCKED` 批量认领。

**为什么**：

1. **量级不需要**：估算峰值 150~170 QPS（推导见 §8.1），单表百万级日增。这个量级下 MySQL 的写能力有近一个数量级余量，且**估算偏差 3 倍以内不改变结论**（§8.3）。
2. **少一个系统 = 少一类故障**：引入 MQ 后要处理"投递到 MQ 成功但 DB 写失败"的一致性问题（正是要避免的双写），排查链路从两段变三段，还要养一套 MQ 集群。
3. **MQ 解决的是"削峰"和"广播"，而这里的瓶颈是下游 HTTP 延迟**，不是接入写入。用 MQ 削峰等于把排队位置从表挪到 broker，没有本质收益。
4. **SKIP LOCKED 已经把行锁竞争消掉了**，多实例并发消费天然安全。

**代价**：

- 轮询有延迟（默认 500ms 一次），对"秒级送达"够用，对"毫秒级"不够。有强时效接入时的分级降法见 §9.8 —— 不需要推翻本方案；
- 数据库承担读写压力，量级再上一个数量级必须换掉；
- 到期扫描是全表索引扫描，需要 `(status, next_attempt_at)` 复合索引 + 归档配合。

**没选**：

- **Kafka**：为 150~170 QPS 引入分区、消费位点、rebalance、运维，收益为零。且 Kafka 的重试需要自己造 topic 和延迟队列——等于把复杂度换个地方存。
- **RabbitMQ 延迟插件 / 死信队列**：语义天然更贴合，但仍是新增一套需要运维的有状态组件。**它是第二阶段的正确答案，不是第一版的。**
- **Redis 做延迟队列（ZSET）**：看起来轻，但引入第二个存储后就有"Redis 有、DB 没有"的一致性问题，且 Redis 持久性不足以保证不丢。**用可靠性更低的东西承载可靠性需求，方向错了。**

### D4｜SKIP LOCKED + 租约：用数据库实现「队列语义」

这一节是整套方案的技术基石。分五步说清：为什么需要锁 → 为什么是 SKIP LOCKED → 为什么还要租约 → 完整 SQL → 五条实现约束。

#### 4.1 第一步：多实例从同一张表取任务，为什么不能直接 SELECT

```sql
SELECT id FROM notification WHERE status='PENDING' AND next_attempt_at<=NOW(3) LIMIT 100;
```

两个实例同时执行，拿到同一批 100 条，各投一遍 → 全部重复。所以必须"**取到即占住**"。三种做法对比：

| 做法                                  | 行为                               | 问题                                                        |
| ----------------------------------- | -------------------------------- | --------------------------------------------------------- |
| 普通 `SELECT`                         | 不加锁                              | 重复消费，不可用                                                  |
| `SELECT ... FOR UPDATE`             | 选中行打排他锁                          | 实例 B 会**阻塞等待** A 提交。实例越多排队越重，吞吐被串行化。它解决"不重复"，但代价是整个表变成单通道 |
| `SELECT ... FOR UPDATE SKIP LOCKED` | 碰到已锁定的行 → **不等待，直接跳过**，继续取下一批可用行 | 无。这是为队列表专门设计的语义（PostgreSQL 9.5 / MySQL 8.0 引入）            |

`SKIP LOCKED` 的效果：每个实例拿到的行集合**互不相交**，且**没有等待**。多实例横向扩展退化成"加机器"这一件简单的事。

#### 4.2 第二步：SKIP LOCKED 只在事务内有效 → 必须同时改状态

事务一提交，行锁就释放。如果只锁不改状态，锁释放后别的实例立刻又能选到同一行。  
所以必须在**同一个事务**里把 `status` 改成 `PROCESSING` —— "占住"这件事从**锁**落到了**数据**上，才跨事务有效。

#### 4.3 第三步：状态标记带来新问题 → 租约

`status=PROCESSING` 之后，如果 worker 被 kill / OOM / 卡在网络黑洞里，这行就**永远停在 PROCESSING**。  
这是最糟的失败形态：任务没投出去，但也没有任何报错——**静默卡死比失败更危险，因为它不告警**。

解法：不给"占有"一个布尔值，而给一个**有效期**。

| 字段            | 含义                   |
| ------------- | -------------------- |
| `lease_owner` | 谁占的（实例 ID，排查用）       |
| `lease_until` | 占到什么时候（= 认领时刻 + 60s） |

实例死掉不会来清理，`lease_until` 自然过期，下一轮扫描把这条重新视为"可认领"。  
这就是**可见性超时（visibility timeout）**，与 SQS 的语义完全同构。

#### 4.4 第四步：完整认领 SQL

```sql
UPDATE notification
SET status       = 'PROCESSING',
    lease_owner  = :instanceId,
    lease_until  = DATE_ADD(NOW(3), INTERVAL 60 SECOND),
    attempt_count = attempt_count + 1
WHERE id IN (
  SELECT id FROM (
    SELECT id FROM notification
    WHERE (status IN ('PENDING','RETRY_WAIT') AND next_attempt_at <= NOW(3))
       OR (status = 'PROCESSING' AND lease_until < NOW(3))      -- ← 崩溃回收就在这一行
    ORDER BY next_attempt_at
    LIMIT :batchSize
    FOR UPDATE SKIP LOCKED
  ) t
);
```

**注意第二条 `OR` 分支**：它不是一条特殊的恢复路径，而只是"**租约已过期的任务，和到期任务一样可认领**"。  
整个崩溃恢复机制就是这一个条件 —— 没有额外的清理定时任务，没有补偿逻辑，没有状态修复脚本。这是我认为这个设计最优雅的地方。

时序（A 崩溃、B 接手）：

```
t=0      A 认领 #42，lease_until = t+60
t=3      A 开始投递 → 进程被 kill（DB 里什么都没变）
t=60     租约到期，状态仍是 PROCESSING，谁也不管它
t=60.x   B 的轮询命中 OR 分支，认领 #42（attempt_count 变为 2）
t=61     B 重新投递 → 供应商收到第二次请求
```

最后一步说明了关键结论：**租约保证"不丢"，不保证"不重"**。  
A 在"请求已发出、结果未落库"之间崩溃，这个窗口物理上无法消除。这既是语义必须是 at-least-once 的根本原因，也是为什么必须给下游幂等标识（D2）。

#### 4.5 第五步：五条实现约束（写错任何一条都会出事故）

1. **`lease_until > HTTP 总超时 + 余量`**。本项目 60s 租约 / 15s 超时。若反过来（租约 10s、超时 15s），A 还在投递租约已过期，B 认领同一条开始投递 → 双投率暴涨。**启动时断言，不满足直接拒绝启动**（任务 T4.3）。
2. **`attempt_count` 在认领时自增，不在完成后**。崩溃时没人能执行"完成后自增"，毒消息会无限循环。
3. **认领事务里绝不放 HTTP 调用**。先认领 + 提交事务，再投递。否则一条 15s 的请求会占着数据库连接，几十个 worker 就把连接池耗尽——把 HTTP 慢变成了数据库不可用，故障放大。
4. **租约时间用数据库 `NOW()`，不用应用时钟**。多实例时钟漂移会让"是否过期"的判断出现分歧，这是最隐蔽的重复投递来源。
5. **`batchSize ≤ 当前空闲 worker 数`**。认领 100 条但只有 30 个空闲 worker，剩下 70 条要排队等租约过期、被别的实例重领 —— 我们**自己制造了重复**。按空闲 worker 数动态计算 LIMIT。

#### 4.6 这一步也顺便论证了"第一版不上 MQ"


SKIP LOCKED + 租约 = **并发消费不重复** + **崩溃后可见性恢复**，恰好是 SQS 最核心的两个语义。  
所以不上 MQ 不是因为"图省事"，而是因为 **MQ 最关键的 20% 语义，我们用一段 SQL 自己实现了**；剩下的 80%（削峰、广播、多消费组、跨机房）在本量级用不上。

代价也写在明面上：轮询带来 500ms 延迟、数据库承担队列读写、量级到 V2 必须换掉（见 §7）。

### D5｜失败分类决定重试策略（最重要的一个判断）

**做法**：

| 结果                          | 分类                   | 处理                        | 依据                                                     |
| --------------------------- | -------------------- | ------------------------- | ------------------------------------------------------ |
| 2xx                         | SUCCESS              | 标记成功                      | —                                                      |
| 400 / 401 / 403 / 404 / 422 | PERMANENT            | **直接 DEAD，不重试**           | 请求本身有问题（字段错、地址错、凭证失效）。重试 10 次结果一样，只是把一次配置错误放大成 10 次报警。 |
| 401 / 403                   | PERMANENT + **高优告警** | 立即通知值班                    | 凭证过期是"静默全面失效"，越早发现越好                                   |
| 408 / 429                   | RETRYABLE            | 重试，429 优先遵守 `Retry-After` | 对方明确表示"稍后再来"                                           |
| 5xx                         | RETRYABLE            | 重试                        | 对方内部故障，可能自愈                                            |
| 超时 / 连接拒绝 / DNS / TLS       | RETRYABLE            | 重试                        | 网络与对方可用性问题                                             |

**为什么这是重点**：AI 给的初版方案几乎总是"失败就重试 3 次"，这是**没有分类的重试**。真实代价是：一个 400 被重试 10 次，占满 worker、拉起告警风暴、并让真正的 5xx 排不上队。

**代价**：分类表需要维护，且不同供应商对状态码的使用不规范（有的用 400 表示"系统忙"）。因此**分类表支持按端点覆盖**，默认走通用规则。

**没选**：把所有非 2xx 都重试 —— 简单，但违反了 1.2 的约束 3（不能重复放大）。

### D6｜退避曲线与「重试预算」

**做法**：

```
delay(n) = min(cap, base × 2^(n-1)) × rand(0.5, 1.5)     -- 全抖动
默认：base=10s, cap=1h, max_attempts=10  →  覆盖约 3.5 小时
预设档位：STANDARD(如上) / LONG_TAIL(cap=2h, max=14, 覆盖约 24h) / FAST_FAIL(max=2)
```

**为什么加抖动**：供应商恢复的瞬间，所有等待中的任务会在同一秒涌出（惊群），把刚恢复的服务再打挂一次。抖动把重试摊平到区间内。

**为什么分档**：付款通知（LONG_TAIL，可等一天）和广告归因（FAST_FAIL，2 小时内不到就没价值了）对"多久算失败"的容忍度完全不同。用一套参数服务所有场景是最常见的偷懒。

**代价**：档位是配置项，需要在接入文档里让业务方显式选择——多一个需要解释的概念。

**没选**：固定间隔重试 → 长尾故障下的重试次数几乎全浪费在前几分钟。

### D7｜端点隔离：熔断与「跳过不计次」

**做法**：按 `host` 维度维护熔断器（滑动窗口 60s，失败率 > 50% 且样本 ≥ 20 → OPEN 60s）。OPEN 期间该 host 的任务不真正发出，直接 `next_attempt_at += 60s`。

**关键细节（容易被漏掉）**：熔断跳过**必须把 `attempt_count` 回退**。  
否则一个供应商挂 30 分钟，会把排队中的健康任务全部"烧"成 DEAD —— 明明是对方的问题，却把我们的重试预算吃光，等对方恢复时任务已经死了。这是"看起来对的实现"里最常见的错。

**为什么需要**：不隔离的话，一个慢供应商会占满 worker 池（HTTP 调用是阻塞的），导致其他供应商全部排队——**故障扩散**。这是需求里"不同供应商"给出的明确信号。

**代价**：多一层状态需要观测（每个 host 的熔断状态要能看到）。首版熔断器只在进程内存，多实例各自独立判断——这是有意的简化：全局熔断需要共享存储，而局部熔断已能保护自身。

### D8｜死信、重放，以及「失败该通知谁」

at-least-once 的另一面是"最终可能失败"。没有兜底的系统不是可靠系统，只是**把失败藏起来的系统**。

#### 8.1 死信就是一个状态，不是一个队列

`DEAD` 即死信。不单独建 DLQ 表/主题 —— 那会多一份数据、多一处可能不一致。用 `status` + `(status, next_attempt_at)` 索引即可查询与统计。

#### 8.2 重放：为什么必须是「显式」的

**自动重放是危险动作，不是优化项。** 一条 `DEAD` 有两种可能：

- 供应商明确拒收（重放必然再失败）；
- 供应商其实已处理、只是响应超时（重放会造成**重复业务动作**）。

**系统无法区分这两者，只有人知道业务上能不能承受重复。** 所以重放的决策权必须在人手里，系统只提供能力。这就是"显式 replay"的含义 —— 它不是技术上的权宜，而是**对边界的有意承认**。

#### 8.3 三种重放路径（只做单条是操作上的失误）

| 场景           | 方式                                                                      | 说明                                      |
| ------------ | ----------------------------------------------------------------------- | --------------------------------------- |
| 单条排查后重发      | `POST /v1/notifications/{no}/replay`，body `{reason, operator}`          | 最小能力                                    |
| 修完凭证/域名后批量恢复 | `POST /v1/notifications/replay-batch`，按 `caller + error_class + 时间窗` 过滤 | **必须有**：凭证过期 1 小时可能积压几千条 DEAD，让人一条条点不现实 |
| 定时自动兜底       | 不做                                                                      | 理由见 8.2                                 |

#### 8.4 重放的四个必要约束

1. **状态守卫，天然防重复点击**
   ```sql
   UPDATE notification SET status='PENDING', ...
   WHERE notification_no = ? AND status = 'DEAD'
   ```
   第二次点击影响行数为 0。不需要额外分布式锁。
2. **前置体检**：批量重放前先对目标端点发一条探测（用最近一条 body，或 GET 目标地址）。**凭证没修就重放 3000 条，等于把 3000 份重试预算再烧一遍**，而且会产生 3000 条新告警把真实问题盖住。
3. **摊平重放**：3000 条不能同时变 `PENDING` 涌向同一个 host —— 那是自己制造惊群，可能把刚恢复的供应商再打挂一次。按 `next_attempt_at = now + i × 200ms` 摊到约 10 分钟。
4. **`replay_epoch` —— 一个真实会踩的坑**  
   如果重放时把 `attempt_count` 归零，`delivery_attempt` 的唯一键 `(notification_id, attempt_no)` 会**直接撞键**，重放失败。正确处理：
   - `attempt_count` **不归零**，保持单调递增（这样毒消息保护才连续有效）；
   - 增加 `replay_epoch`，唯一键改为 `(notification_id, replay_epoch, attempt_no)`；
   - 同时 `max_attempts += 该档位预算`，否则重放后第一次尝试就立刻又超限。  
     附带好处：attempt 记录可按"第几轮"分组展示，排查时能分清"首轮失败"与"修好后的第二轮"。

#### 8.5 失败该通知谁：按错误类型路由，不广播

我们承诺"可靠送达"。如果最终没送达却没人知道，这个承诺就是空的。  
但**广播给所有人 = 没人负责**（告警疲劳会让人关掉通知）。

| `error_class`              | 谁该知道                        | 通道            | 时效  |
| -------------------------- | --------------------------- | ------------- | --- |
| `HTTP_4XX`（400/422，参数错）    | **业务方** —— 他们的 bug，要改代码重发   | 失败清单 API + 日报 | 小时级 |
| `HTTP_401/403`（凭证失效）       | **接口负责人 / 运维** —— 改一个配置能救全部 | 立即告警          | 分钟级 |
| `TIMEOUT` / `HTTP_5XX` 超预算 | **业务方** —— 由他们决定业务是否降级      | 失败清单 API + 日报 | 小时级 |
| `DNS` / `TLS`              | 运维                          | 立即告警          | 分钟级 |
| 熔断 OPEN                    | 运维（供应商侧故障）                  | 告警            | 分钟级 |
| 队列积压超阈值                    | 运维                          | 告警            | 分钟级 |

**首版的通道选型**：

- 运维侧 → Prometheus 规则 → 企业微信/邮件（任务 T5.10）；
- 业务方 → **拉取式** `GET /v1/notifications?status=DEAD&since=<cursor>`，按 caller 鉴权，只能看自己的。

**为什么不用 webhook 推给业务方**：那要求每个业务系统额外实现一个接收端点，并引入"通知系统的通知失败怎么办"的递归问题。拉取式零接入成本，业务方可在自己的定时任务里消费游标。等某个业务方明确提出实时性要求，再加可选 `callback_url`（V1）。

**边界重申**：我们负责"**让人知道失败**"，业务方负责"**决定业务上怎么办**"。  
做业务补偿（重发订单、回滚状态、重算库存）是越界 —— 那需要业务语义，见 §2.2 与 §6 第 11 条。

### D9｜接入侧背压：拒绝优于堆积

**做法**：

- 按 `caller_id` 做令牌桶限流（如 200 QPS），超限返回 `429 + Retry-After`；
- 队列健康度守卫：`PENDING` 积压超过阈值（如 10 万或最大延迟 > 30min）时，新请求直接 `503 + Retry-After`。

**为什么**：这是最反直觉但最重要的一条。通知系统接收请求的成本极低、完成成本极高（依赖外部），**如果没有背压，它会变成无限缓冲区**——上游以为提交成功，实际上任务要几小时后才投。而"几小时后才投的广告归因"等于没投。

**明确表达"我现在处理不了"**，比"我收下了但延迟未知"更负责任。业务系统有能力处理 429（重试或降级），但无法处理"静默延迟 6 小时"。

**代价**：需要业务系统正确处理 429/503（这本身是一个推广成本）。所以默认阈值设得很宽松，只在真正异常时触发。

### D10｜安全：SSRF、凭证、PII

这一块是"真实工程经验"最容易体现、AI 最容易漏的地方。本系统**主动向外发起任意 URL 的请求**，天生是一个 SSRF 放大器。

| 风险                                                | 措施                                                                                                                                       |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **SSRF**（调用方填 `http://169.254.169.254/...` 或内网地址） | ① 出站域名白名单（按 caller 配置）；② 解析后校验**实际 IP**，拒绝私有段/回环/链路本地/`::1`/`fc00::/7`；③ 禁止跟随重定向（或最多 1 跳且重校验）；④ 生产环境强制 HTTPS + 校验证书；⑤ 固定出网出口，网络层再加一道 ACL |
| **DNS rebinding**                                 | 校验用的解析结果与实际连接目标必须是同一 IP（连接层绑定）                                                                                                           |
| **凭证泄露**（Header 里带供应商 API Key）                    | 加密存储（KMS/信封加密），查询接口脱敏返回（`****abcd`），日志不打 Header                                                                                          |
| **PII 留存**（注册/付款事件含手机号、邮箱、金额）                     | body 密封存储；保留期 7 天（成功后 24h）后由归档任务清除明文；日志只打 `body_fingerprint` 与长度                                                                         |
| **越权**                                            | 调用方可查询/重放**仅限自己**提交的通知                                                                                                                   |

**为什么必须写进设计文档**：这是金融业务（RightCapital 属于财富管理领域）与普通后台系统最本质的差别——同样一个"发 HTTP 请求"的功能，在别的公司是工具，在这里是合规风险点。

#### D10.1 两把密钥、两个职责

`headers_enc` 与 `body_enc` 需要**可逆**（投递时要还原字节发出去），所以只能用对称加密，不能用任何哈希。而 `body_fingerprint` 需要**不可逆且可比对**（归档清空 body 后，还要能回答"当时发的是不是这份内容"）。

两者是不同性质的需求，不能合并，也不能用同一把密钥：

| 字段                         | 目标          | 手段                          | 密钥                |
| -------------------------- | ----------- | --------------------------- | ----------------- |
| `headers_enc` / `body_enc` | 机密性 + 完整性   | AES-256-GCM（AEAD，一次运算同时给两者） | `NOTIFY_BODY_KEY` |
| `body_fingerprint`         | 可比对性 + 不可伪造 | HMAC-SHA256                 | `NOTIFY_FP_KEY`   |

密钥分离不是洁癖：密封密钥泄漏时，攻击者能读历史数据，但不该同时获得"伪造任意指纹"的能力——否则归档后的审计链一起塌。

#### D10.2 密封格式与 AAD

|                              |   |                                  |
| ---------------------------- | - | -------------------------------- |
| \`\[1B 版本\]\[12B 随机 IV\]\[密文 |   | 16B GCM tag]`，AAD = `单号 + 字段名\`。 |

- **版本字节**：为算法/密钥轮换留位，否则换密钥那天旧数据全成死数据；
- **随机 IV**：同一明文两次密封得到不同密文——密文相等本身就在泄漏"内容相同"这个事实；
- **AAD 绑定行与字段**：把 A 行的密文搬到 B 行、或把 headers 的密文塞进 body，解密直接失败。这是"密封"相对"明文 + 校验和"多出来的那层保护；
- **在落库之前密封**：明文不经过任何持久化路径，也不进日志。

> **V4 的遗留问题（已实测确认）**：改列类型只改变写入路径，**不会回溯加密已存在的行**——迁移前落库的 body 仍然是明文。真实上线时需要一个一次性的回填任务（读旧行 → 解密失败则视为明文 → 重新密封 → 写回，分批 + 断点续传），并且要在回填完成前保持"读路径兼容明文"，否则历史记录全部读不出来。这是"加解密改造"里最容易被漏掉的一步：**schema 迁移不等于数据迁移**。

#### D10.3 请求体指纹：HMAC-SHA256，而不是 PBKDF2 + 随机盐

这一条来自一次真实的技术评审意见：*"裸 SHA-256 存数据不安全（彩虹表、GPU 暴力破解），生产至少要加随机盐并做多次迭代，用 JDK 的 PBKDF2WithHmacSHA256。"*

**结论：不采纳，但原意见指向的漏洞是真的——只是修复方式选错了工具。**

先说对的部分。这个字段确实有可被反推的风险，因为**本系统的 body 熵很低**：库存回调可能只是 `{"sku":"A-100","delta":-10}`，付款回调可能只有 `{"status":"paid"}`。裸摘要对这种输入等价于可逆——任何拿到数据库的人都能枚举候选明文做比对。"加一把密钥"确实是正确方向。

但 **PBKDF2 是口令派生函数，不是本文用途的工具**，两个理由都是硬伤：

| 维度      | 本字段的要求                  | PBKDF2 + 随机盐                                                                                          | 结论                     |
| ------- | ----------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------- |
| **确定性** | 相同明文必须得到相同指纹（否则归档后无法比对） | 随机盐 → 相同明文得到不同值                                                                                       | **用途被直接破坏**            |
| **成本**  | 每条受理算一次，热路径             | 210k 次迭代（OWASP 2023 档）在本机实测 **30.7ms**，是 SHA-256 的 **28803 倍**；150 QPS 下纯哈希需 **4.6 个 CPU 核**（本机仅 8 核） | 与"受理接口 p99 < 50ms"直接冲突 |

慢哈希的设计前提是"**验证一个人输入的口令**"——低熵、低频、一次性；而这里是"**每条消息都算一次的可比对指纹**"——高频、要求确定。把前者套到后者，等于用刹车片做发动机。

**正确的修复是"密钥化"而不是"加盐 + 迭代"**：`HMAC-SHA256(明文, 服务端密钥)`。

- 没有密钥的人无法构造候选摘要 → 低熵 body 推不出来（这是"盐"想要的防护）；
- 仍然确定性 → 归档清空 body 后可比对；
- 仍是一次哈希（实测 0.00107ms/次，与裸 SHA-256 持平）→ 热路径无感。

一句话：**盐解决"相同输入产生不同输出"，而这里恰恰需要相同输出。** 需求方向相反，不能靠调参补救。

> 顺带一条自我检查：这套系统里**没有任何地方需要 PBKDF2/bcrypt/argon2**——它没有"用户输入的口令"。如果将来接入控制台出现人工设置的密码，那时才是它该出场的地方。工具用错地方，比不加密更有害，因为它会让人以为已经处理过了。

### D11｜可观测性：三个必须能回答的问题

不是"接一堆监控"，而是明确要能回答三个问题：

| 问题           | 手段                                                                          |
| ------------ | --------------------------------------------------------------------------- |
| 现在健康吗？       | 指标：接入 QPS/错误率、队列深度、**最老待投任务年龄**（比队列深度更准）、投递成功率、p95 投递耗时、各 host 失败率与熔断状态、死信数 |
| 这条为什么没到？     | `notification_no` 一查到底：状态机轨迹 + 每次 attempt 的状态码/错误分类/耗时/响应片段                 |
| 是不是某个供应商的问题？ | 按 `host` 维度聚合失败率，直接定位是"单点故障"还是"全局问题"                                        |

**取舍**：首版不接分布式追踪（Jaeger/OTel）。用结构化日志 + `notification_no` 贯穿即可定位。理由是投递链路只有 2 跳，追踪的收益要等链路变长才显现。

## 6. 我认为「过度」并明确不采纳的方案

这一节是作业的评估重点。但列一张"我拒绝了什么"的清单不够 —— **拒绝必须有可复用的判据，否则只是个人口味**。所以先给判据，再给清单，并标注每条触发了哪几把尺子。

### 6.1 判据：6 把尺子，且区分「硬约束」与「软权衡」

**硬约束（违反即方案不成立，不参与收益权衡）**

| 尺子         | 问题                 | 为什么是硬的                                                      |
| ---------- | ------------------ | ----------------------------------------------------------- |
| **A｜归属**   | 这件事本来是不是我的职责？      | 越界的能力无论做得多好都是负债 —— 它会与真正的责任方产生两套并存的语义，出问题时双方都不认账            |
| **B｜净故障面** | 它新增的失败模式，是否多于它消除的？ | 每个新组件都带来新故障（网络分区、版本不兼容、脑裂、配置漂移）。"消除 1 类问题、引入 3 类问题"的交换永远不划算 |

**软权衡（需与收益比较，条件变化时允许翻案）**

| 尺子         | 问题                               | 判断要点                                              |
| ---------- | -------------------------------- | ------------------------------------------------- |
| **C｜必要性**  | 解决的是**已发生**的问题，还是**想象中**的问题？     | 判据不是"将来会不会"，而是"现在有没有观测数据"。没有数据的预优化，收益是猜的，成本是真的    |
| **D｜替代性**  | 同一目的，有没有更便宜的等价手段？                | 多数"高级方案"想买的效果，能用契约、约束或数据模型换来。买贵的之前先问"这个效果能不能用规则换" |
| **E｜位置**   | 复杂度加在**我可控的代码里**，还是**运行时不确定性上**？ | 前者出问题能读代码定位，后者只能靠经验和运气。同等收益下永远选前者                 |
| **F｜可解释性** | 出问题能否归因、能否测试、能否预测？               | 不可解释的机制在生产环境是负债而非资产 —— 它把"故障"变成"玄学"               |

### 6.3 这套判据的自我限制

1. **A/B 是硬的，C~F 是软的。** C~F 任一不过关不等于否决，只说明"需要更强的理由"；真正不能过的是 A 和 B。
2. **通过 6 把尺子 ≠ 必须采纳。** 尺子只做**证伪**，不做证明。全过之后还要问"价值是否大于成本"—— 这一步没有公式，是判断。
3. **可翻案。** 每条都写了触发条件（见 §7）。今天的过度设计，量级变化后可能变成最小必要设计。判据的价值就在于它能说清"**什么时候该翻案**"，而不是给一个永久结论。

## 8. 容量与量级假设

**先说明：这些是假设，不是测量值。** 我拿不到业务方的真实数据，所以做法是"给一个量级区间 + 证明结论对该区间的误差不敏感"。这比假装精确更有用。

### 8.1 推导方法：用「最坏 10 分钟」而不是「日均 × 系数」

均值乘一个拍脑袋的系数是最容易骗自己的算法。改用三个口径交叉，取上界：

| 步骤         | 计算                                                         |
| ---------- | ---------------------------------------------------------- |
| ① 日均量      | 假设 100 万条/天（注册 + 付款 + 下单三类场景合计，含一条事件触发多条通知）                |
| ② 日均 QPS   | 1,000,000 ÷ 86,400 ≈ **11.6**                              |
| ③ 业务集中度    | 假设 70% 集中在 10 小时（8:00–18:00）→ 700,000 ÷ 36,000 ≈ **19.4**  |
| ④ 最坏 10 分钟 | 假设营销推送/活动开抢后集中回流，10% 的量压在 10 分钟内 → 100,000 ÷ 600 ≈ **167** |
| ⑤ 设计点      | 取 **150 QPS**（④ 是单点极端，不完全持续）；容量校验按 200 QPS 做               |

> ③④ 的口径比"日均 × 3"更接近真实分布：通知类流量的尖峰由**业务事件**驱动（一次推送、一次开抢），而不是均匀的日间系数。这也是我最初写"×3 倍 = 100 QPS"时不自洽的地方 —— 11.6 × 3 = 35，得不到 100。已修正为上面的算法。

### 8.2 由此推导的资源需求

| 项             | 推导                                         | 结论                                  |
| ------------- | ------------------------------------------ | ----------------------------------- |
| 有效 QPS（含重试）   | 150 × 1.15 ≈ **172**                       | 重试放大系数取 15%                         |
| Worker 并发（均值） | Little's Law：N = λ×W = 172 × 0.2s ≈ **34** | 均值只需 34 个并发                         |
| Worker 池大小    | 按"供应商整体变慢到 1s"设计 = 172 × 1 ≈ 172           | 取 **200**                           |
| 单条记录          | ~2KB（含 body）                               | 日增 2GB，含索引与 attempt ≈ **4GB/天**     |
| DB 写入 TPS     | 172 次状态更新 + 172 条 attempt 记录 ≈ **350 行/秒** | 单实例 MySQL 约 3000+ TPS → **余量 ~9 倍** |

**为什么要 200 个 worker 而不是 34**：均值 34 意味着平均利用率只有 17%。多出来的部分买的是三件事 —— ① p99 = 3s 的尾部延迟；② 尖峰时的瞬时并发（167 QPS 那 10 分钟）；③ 某个供应商变慢时不至于让整个队列排队。**但池子不能无限加**：200 并发仍不够，说明供应商真的挂了，此时该做的是熔断（D7），不是继续加线程。

### 8.3 敏感性分析（这才是"取舍站得住"的关键）

关键问题不是"150 这个数字准不准"，而&#x662F;**"猜错了会不会改变技术选型"**：

| 日通知量          | 峰值 QPS   | DB 写入余量 | 结论                    |
| ------------- | -------- | ------- | --------------------- |
| 30 万          | ~50      | ~27×    | DB 明显够，甚至可以降配         |
| **100 万（基准）** | **~170** | **~9×** | **DB 够用，V0 方案成立**     |
| 300 万         | ~500     | ~3×     | 开始临界，启动 V1（归档 + 读写分离） |
| 1000 万        | ~1700    | ~1×     | 必须上 MQ（V2）            |

**结论**：估算偏差在 3 倍以内，技术选型完全不变；要到 **10 倍**才会翻转结论。  
所以"用 DB 当队列"这个决策是**对估算误差鲁棒的** —— 这比"我算出了 150 QPS"更有说服力。

### 8.4 上线后如何把假设变成事实

1. 接入前向业务方要三个数：日事件量、峰值时间窗、单事件触发通知条数的分布；
2. 上线首周把「实际峰值 QPS / 实际 p99 耗时 / 最老待投任务年龄」与本文档对比，偏差超 3 倍则重跑本节；
3. 预留配置项（worker 池大小、batchSize、lease 时长），使调整不需要改代码 —— 这也是 T1.3 要求"代码内无魔法数"的实际用途。

## 9. 我可能判断错的地方（待验证假设）

诚实列出，这也是"主动管理复杂度"的一部分：

1. **调用方是否愿意处理 429/503？** 若业务方坚持"必须永远返回成功"，背压机制需要改为"接收但降级为低优先队列"——那会引入本不想要的复杂度。**接入前必须确认。**
2. **供应商对 4xx 的使用是否规范？** 若大量供应商用 400 表示临时故障，分类表的默认规则会导致误判为永久失败。**需在接入前用真实响应校准，并为每个端点保留覆盖能力。**
3. **企业内到底有几个业务系统？与外部供应商是否一一对应？** 需求文档给不出答案，只能肯定"不止一个"（§2.4）。我按**多对多**设计，`caller_id` 只表示提交身份而不是部署单元，所以 1 个或 3 个都不改结构。**接入前需向业务方确认两件事**：① 三个场景分别由哪个系统发出；② 是否已有事件总线 —— 若有，我这一层可以进一步退化为纯投递引擎，连接入 API 都能省掉。
4. **删掉 `ordering_key` 是否删早了？** 前提是三个场景之间没有跨通知的因果依赖。**若有调用方提出"同一实体的两条通知必须按序到达"并能说清业务后果**，则按 §3.5 的槽位表方案加回（加列 + 加索引，无迁移）。这是唯一一处我可能"收敛过头"的地方，我把它写在这里而不是藏在心里。
5. **7 天 PII 保留期是否满足合规？** 这是法律/风控问题，不是技术判断，需要与合规确认。
6. **容量假设可能偏一头。** §8 的 150~170 QPS 是从业务场景反推的假设，真实值可能差 3 倍以上。我已用敏感性分析证明"3 倍内不改变选型"，但若实际是 10 倍，V2 必须提前到首版之后立刻启动。
7. **批量重放的"前置体检"能否真的判断出端点已恢复？** 一次探测请求成功不代表全量能成功（可能是限流刚好没触发）。这是一个概率性判断，不是保证 —— 所以批量重放仍需人工确认，不能做成"体检通过就自动全量重放"。
8. **轮询 500ms 的延迟，强时效业务接入时改造成本高吗？** 不高，降法分三级，前两级都不引入新组件：
   - **① 调配置（零代码）**：轮询间隔是预留配置项（T1.3），可降到 50ms。空闲 DB QPS 从每实例 2 涨到 20，仍可忽略。适合"偶发强时效"。
   - **② 提交后唤醒（insert-then-hint，一个小类）**：V0 是模块化单体，接入 API 与 Dispatcher 同 JVM。落库成功后直接把 `notification_id` 塞进内存交接队列，Dispatcher 立即认领，绕过等待。**提示丢了也无所谓**——轮询 500ms 后照常兜底，所以正确性语义（at-least-once）完全不变，hint 只是把 p50 受理延迟从 ~250ms 压到 ~10ms。DB 仍是唯一事实来源，内存队列不是。
   - **③ 跨实例信号（多实例后才需要）**：hint 只唤醒本 JVM；多实例部署时其他实例仍靠轮询。真出现瓶颈再上 Redis pub/sub —— 那是第一次引入新组件的时机，之前都是免费的。
   - **绝不选 DB 触发器 + 事件通知**：逻辑藏在数据库里、无法单测、触发器与 binlog/复制的交互行为不可控。上一版文档我曾把这个列为备选，是错的。
   - 还有一个必须先问的问题：**"强时效"指我方受理延迟，还是端到端送达？** 端到端里我方只占一小段，外部供应商的处理延迟往往比 500ms 大一个数量级——先要数据再优化。若业务方说"必须 1 秒内送达且失败要实时可见"，那这个场景大概率**不该走本系统**（§1.1：异步通知的定位是"业务系统不关心返回值"；验证码类同步交互应该同步调用）。边界判断优先于性能优化。

## 11. P4 投递引擎实现注记（代码与设计的对齐）

写这一节的动机：设计文档最容易在实现阶段悄悄失真 —— 一开始写"三段超时"，写代码时发现客户端只有两段，于是代码和文档各说一套，半年后没人知道哪个是真的。**实现与设计不一致时，只有两种正确做法：改代码，或者改文档并说明理由。这里记录的是后者。**

### 11.1 与任务清单不一致的三处

| 任务清单原文 | 实际实现 | 为什么改 |
|---|---|---|
| T4.4「connect 3s / read 10s / total 15s」 | connect 3s + total 15s（两段） | JDK `HttpClient` 只有 connectTimeout 与整请求 timeout，**没有独立的 socket read timeout**。为了补齐第三段而引入 Apache HttpClient，换来的是一个已被总超时覆盖的能力 —— 多一个客户端、多一套连接池、多一类故障。代价大于收益，所以改清单 |
| T4.7「响应片段截断 2KB」 | 按 **2048 字符**截断 | `response_snippet` 是 `VARCHAR(2048)`，列宽按字符定义。按字节截会在多字节字符上切出乱码，还会让"存了 2KB"和"列能装 2K 字"两个说法打架 |
| T4.2「认领条数 ≤ 空闲 worker 数」 | `min(batchSize, 空闲槽位)` + 单条 `claimByNo` 路径 | hint 唤醒需要"按单号精确认领"。两条路径必须共用同一套状态守卫（`status IN ('PENDING','RETRY_WAIT') AND next_attempt_at <= now`），否则 hint 会绕过退避把任务提前发出去 |

### 11.2 三个实现时才想清楚的约束

1. **落状态必须带 `lease_owner` 守卫。** 一次投递耗时超过租约（GC 长停顿、网络黑洞）时，租约会被别的实例回收并重投；此时旧 worker 手里的结果已经过期。不带守卫地写状态，会出现"旧结果覆盖新结果"：新 worker 已经判 DEAD，旧 worker 慢悠悠写回 SUCCEEDED。守卫失败（影响 0 行）不是错误，是设计内的竞争 —— **丢弃结果 + 计数 `notification.delivery.zombie`**，绝不重试写入。这个指标持续大于 0，说明租约时长与真实耗时不再匹配。

2. **hint 是提示，不是队列。** 队列满、进程重启、多实例部署都会让它丢；丢了通知仍在 MySQL 里，500ms 轮询兜底，语义不变。正因为它是"可丢弃的加速提示"，才能用有界队列 + 静默丢弃。**若按可靠队列设计，就得为它做持久化和重投 —— 那等于在 MySQL 之外再养一个队列，把"数据库即队列"的初衷推翻。**

3. **抢不到 host 许可必须回退 `attempt_count`。** 这类"没发出去"不是一次尝试。照常计数的话，供应商挂 30 分钟，健康任务会被自己的调度逻辑耗成 DEAD，等对方恢复时任务已经死了（这就是 D7 熔断跳过的同款问题，P5 的熔断会复用同一个方法）。实现上有个细节：列是 `SMALLINT UNSIGNED`，`attempt_count - 1` 减到 -1 会直接报 "Out of range value"，所以用 `GREATEST(attempt_count, 1) - 1`。

### 11.3 一个只有跑起来才会发现的问题：集成测试被自己的调度器污染

P4 落地后，`NotificationRepositoryIT` 的并发认领用例开始偶发失败：200 条记录里总有十几条没被认领，而且**每次失败的行还不一样**。

第一反应是 `SKIP LOCKED` 有饥饿问题，差点去改 SQL。查库才发现那几条记录的状态是 `DEAD` —— 它们根本没丢，而是**被投递了 10 次后进了死信**。

原因：`@SpringBootTest` 会把整个应用拉起来，包括 `DispatcherPoller` 的 `@Scheduled`。后台线程每 500ms 认领一次测试刚插入的行，对着 `hooks.vendor.example.com` 真发 HTTP，DNS 失败 → 重试 → 预算耗尽 → DEAD。测试断言的"未被认领"其实是"被后台线程认领并投递完了"。

修法不是加 sleep，而是给调度器一个 `notification.dispatch.auto-start` 开关（默认 true），三个 IT 全部置 false、改为手动调用 `pollOnce()`。**教训：一旦系统有了后台循环，"单元测试"和"集成测试"的边界就变了 —— 测试数据会变成生产行为的输入。**

### 11.4 已知局限（P4 范围内主动不解决）

1. **响应体完整读入内存**，只有 15s 总预算兜底，没有大小上限。换成 `ofInputStream` 可以加上限，但它不受 request timeout 约束 —— 一个只发响应头不发体的下游能把 worker 线程永久挂住。两者相权，选了"内存风险有限、线程安全确定"的一侧。真正的上限属于 P6 出站安全。
2. **`response_snippet` 明文落库。** 请求侧的 body/headers 已 AES-GCM 密封，响应侧没有 —— 下游返回体里可能带 PII。这是 D10 加密范围的一处不一致，P6 一并处理（要么加密，要么只存前 512 字节 + 摘要）。
3. **失败退避是固定 30s**（`retry.fixed-delay-seconds`）。P4 只需要状态机闭环，指数退避 + 抖动 + `Retry-After` 下界在 P5 用 `BackoffCalculator` 替换，替换点只有一个（`NotificationStateWriter#settleFailure`）。
4. **hint 不跨进程**：多实例部署时其他实例仍靠轮询。这是设计内的取舍（§9.8 第 ③ 级），不是缺陷。
